# 🌐Social Media Platform CLI

## ✅Prerequisites
- JAVA 21 or later
- Maven 3.9 or later
- Internet connection for maven downloads

## 🗝️Dependencies
- Hibernate Core 7.1.10
- HikariCP 7.0.2
- H2 Database 2.4.240
- Gson 2.13.2
- Jackson Core 2.19.2
- Jackson Datatype JSR310 2.20.0
- JUnit Jupiter 6.0.1
- JUnit Jupiter Params 6.0.1

## 🧩How to run

---
- Open the pom.xml file in IntelliJ to open it as a project
- Run a Maven clean, compile and test
- Start the application by running main.java 
- Sample data will be automatically seeded for you if none exist
- Pick a User to browse the application as, this is currently a requirement

## 🚀Purpose

---
The purpose of this application was to learn how to utilize Hibernate ORM
lambdas, sealed interfaces and the Streams API to simulate in a small and 
controlled environment the backend fundamentals underlying a social media
plattform for educational purposes. With no frontend collaborators DTO presentation 
is still done in CLI-format.

## 🏛️Architecture

---
Limited understanding of idiomatic architecture of service, repository and presentation layers
in the beginning has led to an architecture that leaves a lot to be desired. The handling for our
**Entity Manager Factory** was the only one given serious consideration and is chained from a 
single instance to avoid conflicts with our test unit. Our repository instances and instances 
of our service layer is created on demand in every method who uses them which is not ideal but 
doesn't matter in an application of this small size. Our service and presentation layers are also 
not as clearly separate as they should be. 

## 📊Database Structure

---
Our Database is generated automatically and no schema is used to manually create tables. 
We have set it up so that the tables needed are generated by the respective entities and 
all the join tables are fields in them utilizing collections. We utilized create-drop for a
long time given that the database is to be git ignored anyway, but we have a generative method 
that can be used to generate testdata on demand for any new users.

## 💻Features

---
We tried to get the basic functionality implemented. It is possible to select any user from the database
onm the startup of the application, one can create new users, posts and comments. Hashtags can be added 
to any post. Posts can be liked by other users. We have data analytics methods to display statistics
and methods to export backups of different entities to .json format. 

## 🧑🏻‍🎓Utilization

---
From our studies what we have primarily utilized and focused on is the Streams API, Sealed Interfaces
Lambda Expressions, SQL-queries and custom Exception handling. We have also written a good chunk of tests
for all of our repositories and a bit of the service layer to.

## ⛔Limitations

---
There is currently no admin feature implemented. One must run the simulation as a User who exists 
in the database. This is currently the case because of the join tables between users which means 
trying to use something like the Follow function would break the application if it was browsed without
seeding a Users object throughout our currentUser variable.

## 💎Things to Improve

---
The architecture leaves a lot to be desired and several features could be added like the 
ability to browse as an administrator. The problem is that when knowledge quickly increases
during an intense assignment like this one you quickly reach a point where a complete rewrite 
almost seems like the faster option.
